# 실험 기록 (Experiments)

> 하네스의 산출물은 코드가 아니라 **측정 결과**다 — 이 문서가 그 결과의 누적 장부다.
> 시험지는 [task-ladder.md](task-ladder.md), 설계 근거는 [multi-model-harness-design.md](multi-model-harness-design.md).
> `runs/`는 gitignore 대상(원시 산출물)이므로, 여기에는 요약·해석만 남긴다.

## 측정 원칙

- **중단(harness_abort)은 게이트 실패가 아니다.** 파이프라인이 게이트에 도달하기 전 크래시한
  것(API/인프라 오류)과 게이트가 돌아 red를 낸 것은 전혀 다른 사건이다. 통과율의 분모는
  **완주한 런(pass + gate_fail)** 뿐이다 — 중단을 실패로 세면 통과율이 거짓이 된다.
- 결과 분류는 `runs/<id>/final_report.json`의 유무로 가른다: 있으면 게이트 판정(pass/gate_fail),
  없으면 중단. (Python 미처리 예외는 종료 코드 1로 떨어져 게이트 실패와 구분되지 않으므로,
  종료 코드로는 가를 수 없다 — `scripts/repeat_l1.py`가 이 신호로 분류한다.)

### 읽어낼 것

1. **완주하면 정답에 수렴한다.** 끝까지 돈 2개 런 모두 게이트 green이고 `order.complete()`를
   정확히 복원했다. 153745도 게이트에 도달한 단계(loop1)에서 정답이 이미 diff에 들어가 있었다 —

2. **최소 변경 수렴은 아직 미달.** ground truth는 1줄인데 통과 런의 diff는 +118 / +11줄이다.
   런 간 편차도 10배 — "최소 변경으로 고쳐라" 지시가 실제로 변경 크기를 누르고 있는지는
   조건을 통제한 반복으로 더 봐야 한다(L1-5를 고른 본래 목적: 최소 변경 측정).
3. **중단 3건의 정체.** 154842/154855는 첫 spec 생성 직후 12~15초 만에, 153745는 dev loop2에서
   크래시했다. 게이트 red가 아니라 모델 호출 단계의 예외다. 다음 배치 전에 어댑터에 재시도/백오프를
   넣어 중단율부터 떨어뜨려야 통과율·수렴 지표가 신뢰할 만한 표본이 된다.

### 이 배치에서 하네스에 반영한 것

- `scripts/repeat_l1.py`: 결과를 `pass / gate_fail / harness_abort` 3분류로 분리(이전엔 중단을

### 읽어낼 것

1. **재시도/백오프가 지배적 실패 모드를 제거했다.** E0의 중단 3건(모델 호출 단계의 일시적
   API/CLI 오류)이 E1에서 0건. 중단은 게이트와 무관한 pre-gate 크래시였으므로, 이 감소는
   `adapters/retry.py`에 직접 귀속된다.
2. **최소 변경 수렴 달성.** E0의 +118/+11줄과 달리 E1은 전 런이 +1~3줄(ground truth=1줄)로
   수렴했다. 게이트를 `cleanTest`로 강제 실행해 **fresh DB에서 실제로 25개 테스트가 돈 진짜
   green**(런당 `:app:test` 29초)임을 확인했다 — 캐시 적중으로 스킵된 거짓 green이 아니다.
3. **wall은 E0와 직접 비교 불가.** E1이 ~120초로 빠른 것은 한 방 수렴(dev 루프 1·diff 최소)
   덕이 크지만, 게이트 명령(reset_infra + cleanTest)도 함께 바뀌어 교란이 있다. 귀속이 명확한
   결론은 "중단 제거"이고, wall 단축은 부수 관찰로만 기록한다.

### 재측정에서 드러난 측정 무결성 결함 (모두 수정)

게이트가 ground truth이려면 결정론적이어야 한다. 재측정 준비 중 이를 깨던 결함 4건을 찾아 고쳤다:

- **타깃 repo 오인**: 하네스 대상은 전용 클론 `edc-harness-target`(`.env`의 `HARNESS_TARGET_REPO`).
- **DB 볼륨 오염**: mysql/kafka named volume에 행이 누적돼 `SettlementBatchTest`가 거짓 red
  (`expected 5 but was 65`) → E0 run 153745 gate_fail의 정체. `--reset-infra`로 런 간 `down -v`.
- **Gradle 캐시 스킵**: 수정이 msa와 동일하면 `:app:test`가 up-to-date로 스킵(3초 green) → 테스트
  미실행. `cleanTest`로 강제 재실행해야 reset_infra가 의미를 가진다.
- **드라이버 run 디렉터리 탐지**: `max(iterdir())`가 디렉터리 대신 파일을 집던 버그 → `is_dir()` 필터.

## E2 — 결함 유형별 편차 (L1-1~L1-5 매트릭스)

1. **하네스가 결함 유형을 가리지 않는다.** 멱등성·캐시·배치·보안·상태 5종 모두 완주 시 100% 통과·정답
   복원. **전 결함·전 런 dev 루프=1** — L1 결함은 예외 없이 한 방에 수렴(게이트 루프백 0).
2. **수렴 크기는 결함의 구조 크기를 따른다.** 단일 토큰 결함(L1-3 연산자·L1-5 한 줄)은 diff +1로
   편차 거의 0. 다중 라인 구조 결함(L1-1 dedup 블록)은 +4~15로 편차가 가장 크다 — 블록 복원 방식이
   런마다 달라서다. 즉 "최소 변경 수렴"의 타이트함은 결함이 한 점이냐 한 블록이냐로 갈린다.
3. **wall은 결함 난이도 신호가 아니다.** 유형 내 편차(예: L1-2 78–308초)가 유형 간 차이보다 크다 —
   모델/CLI 지연 변동이 지배적. 평균(113–171초)에 유의미한 유형 서열 없음.
4. **잔존 중단 1건은 새 실패 모드다.** L1-3의 중단은 E0식 transient API 오류가 **아니라**, 기획 단계에서
   모델 출력을 JSON 파싱하다 난 `JSONDecodeError: Invalid \escape`였다(critique까지 쓰고 dev 전 크래시).
   retry는 어댑터 일시 오류를 잡지만 이건 오케스트레이터 파싱 취약점이라 안 잡힌다 — 별개 과제.

## L3 — 기능 개발 측정 (숨긴 인수 테스트): order-cancel

> 첫 **레벨 3** 배치. 회귀 게이트(기존 25개)는 "동작을 안 깨뜨렸나"만 보므로, 신규 기능이
> 실제로 맞게 구현됐는지는 **사람이 사전 작성해 모델에 비공개한 인수 테스트**로만 판정된다
> (게이트 직전 1회 주입, 실패 로그 비피드백 — SWE-bench 구조). 이 배치가 측정하는 핵심
> 신호는 통과율이 아니라 **오구현(`regress_green_accept_red`)** = 회귀 green인데 인수 red.

- **태스크**: L3-order-cancel — `POST /api/orders/{id}/cancel`. CREATED만 취소 가능(200+CANCELED),
  COMPLETED/FAILED/이미취소는 409, 미존재는 404. 변별점: ① 409 상태충돌 의미론(naive가 500/400/200으로
  틀리기 쉬움) ② `CANCELED` 신규 상태값은 **Flyway 마이그레이션으로 DB ENUM을 확장해야** 영속화된다
  (spec에 명시 경고). 숨긴 인수 4개(`tasks/level3/order-cancel.acceptance.java`)는 순수 블랙박스 HTTP.
- **조건**: 기본 설정 — GPT-5.1 기획·리뷰 + Claude(CLI) 비평·구현 (E1·E2와 동일).
- **반복**: 5회. **드라이버**: `repeat_task.py --tasks L3-order-cancel --repeat 5 --reset-infra`,
  게이트 `HARNESS_TEST_COMMAND=".\gradlew.bat cleanTest test"`. 인수는 모델 종료 후 주입·1회 실행,
  판정은 인수 클래스 JUnit XML로만(전체 exit code 아님 — 거짓 통과·flaky 오염 차단).
- **실행일**: 2026-06-17

### 읽어낼 것

1. **오구현이 결정론적으로 재현된다 — 단일 근본 원인.** 5런 전부 동일하게 인수 4개 중 2개 red.
   모델 diff 전수 검사 결과 **5런 모두 `CANCELED`를 Java enum에만 추가하고 Flyway 마이그레이션은 0건**
   (db/migration·`V4__`·`.sql`·신규파일 전무). spec이 명시 경고한 바로 그 함정에 100% 빠진다 —
   상태 머신·409 핸들러·컨트롤러는 다 맞게 짜고, **영속 계층(DB ENUM 확장)만 빠뜨린다.**
2. **실패하는 2개는 'CANCELED를 실제로 저장하는' 경로다.** `cancel_created→200`,
   `이미취소 재취소→409`는 CANCELED를 DB에 써야 하는데 ENUM이 거부('Data truncated')→red.
   반면 `COMPLETED→409`(쓰기 전 예외)·`미존재→404`(쓰기 도달 안 함)는 green. 2/4 분포가
   영속화 도달 여부와 정확히 일치 — 오구현의 위치가 한 점(마이그레이션 누락)으로 좁혀진다.
3. **숨긴 인수 테스트가 없었다면 5/5 전부 '거짓 성공'으로 보였다.** 회귀 게이트만 보면
   5런 모두 green = 100% 통과. L3의 검증 격차(게이트가 신규 요구를 직접 못 봄)가 실재함을
   이 배치가 처음으로 **측정**했다. 인수 클래스 XML 기반 판정이 이 격차를 메운 장치다.
4. **기획 비평도, 모델 자기 테스트도 이 누락을 못 잡았다.** 144602는 비평 1왕복(기획 rev 2)을
   거쳤는데도 동일 오구현. 모델 자기테스트는 전 런 0건(`model_wrote_tests=0`) — 스스로 영속화를
   검증할 테스트를 안 썼다. 즉 누락은 **리뷰·자가검증 양쪽 그물을 다 빠져나간다** → 다음 레벨(L4,
   모델이 테스트까지 작성)에서 이 지점이 바뀌는지가 자연스러운 후속 질문.
5. **수렴 지표는 L1과 동결.** dev 루프 전 런 1, diff +41~52(평균 ~44, 편차 좁음), wall 113~169초.
   회귀 게이트 기준으로는 한 방 수렴 — 모델은 **자기가 만든 결과가 틀렸다는 걸 게이트로부터
   알 수 없다**(인수는 비공개). 오구현이 루프백을 유발하지 않는 게 이 레벨 측정의 본질.

### 이 배치에서 하네스에 반영한 것

- `reset_infra(repo, services=None)`: 게이트 필수 서비스만 선택 기동 가능하게 인자 추가
  (`scripts/repeat_l1.py`). 관측 전용 `grafana`가 호스트 포트 3000을 다른 프로젝트 dev 서버와
  다투면 `docker compose up`이 exit 1 → reset 전체가 `infra_fail`이 되던 문제. `repeat_task`는
  `GATE_SERVICES`(mysql/redis/kafka/prometheus, grafana 제외)만 넘긴다. 기본 None이면 기존처럼
  전체 up이라 L1 경로는 불변. (이 배치 첫 시도가 이 충돌로 5/5 infra_fail → 수정 후 재측정.)
