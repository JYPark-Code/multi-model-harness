# Feature: 주문 취소 API (상태 기반 취소 규칙)

> 하네스 입력(태스크). 이 문서는 모델에게 주어진다 — 요구사항만 담고, 채점용 인수
> 테스트의 구체 케이스/검증 방식은 담지 않는다(숨긴 테스트가 ground truth이므로).

## 배경

현재 주문 도메인에는 주문을 취소하는 방법이 없다. 접수만 된 주문을 고객이 되돌릴 수
있어야 한다. 단, 이미 처리가 끝났거나 실패한 주문까지 임의로 되돌리면 후속 처리·정산과
불일치가 생기므로, **상태에 따라 취소 가능 여부가 갈려야** 한다.

## 요구사항

- 새 엔드포인트: `POST /api/orders/{orderId}/cancel` — 해당 주문을 취소한다.
- **취소 가능 조건**: 주문 상태가 `CREATED`(접수만 된 상태)일 때만 취소할 수 있다.
- 취소에 성공하면 주문 상태를 `CANCELED`로 바꾸고, **HTTP 200**과 함께 갱신된 주문 정보
  (기존 주문 조회와 동일한 `OrderResponse` 형태)를 반환한다.
- **취소 불가 상태**: 주문이 이미 `COMPLETED`이거나 `FAILED`이면 취소할 수 없다 → **HTTP 409**.
- 이미 `CANCELED`된 주문을 다시 취소하려 하면 → **HTTP 409** (멱등이 아니라 충돌로 본다).
- 존재하지 않는 `orderId`를 취소하려 하면 → **HTTP 404**.

## 비범위 (스코프 최소)

- 동기/비동기 주문 접수, 조회, 캐시·정산·보안·복제 로직을 바꾸지 않는다.
- 기존 응답 계약(201/202/200/404)을 바꾸지 않는다. 취소는 새 경로로만 추가한다.
- 취소 시 환불·재고 복원 같은 추가 도메인 동작은 범위 밖이다(상태 전이만).

## 합격 기준

1. 기존 통합 테스트 25개 green (회귀 없음).
2. 숨긴 인수 테스트(사람 작성, 비공개) 통과 — 상태별 취소 동작과 HTTP 코드를 검증한다.

> 2번은 네가 작성하는 테스트가 아니다. 요구사항을 정확히 구현하면 통과한다.
> 자체 테스트를 추가로 작성해도 좋으나, 그것이 성공 판정 기준은 아니다.
